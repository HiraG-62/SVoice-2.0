# phase5-voice-rules: 新しい送信データ形式と聞こえる条件の更新（システムアップデート）

大改修フェーズ 5（システムアップデート）の 1 本目。Minecraft 側の送信データの形式が変わり、聞こえる条件に「サーバー」「音楽」「ラジオ」「その他のディメンション」の扱いが加わる。
**聞こえる条件の正は `docs/VOICE_RULES.md`（2026-11-04 にユーザーと確定）。** これと 1 つでも違う判定をしてはいけない。前提知識は `AGENTS.md` と `docs/DESIGN.md`。

## 背景
- 新しい送信データの実物は `docs/data/送信データ/`（git 管理外。実際のプレイヤー名を含むので、内容をコミットやログに出さない）。送信側のコードは同フォルダーの `Minecraft側送信データ.js`。
- 主な変更: 座標とディメンションが `location` の下に入り、`location.server` が加わる。トランシーバーとラジオは `{ type, number }`、声の範囲と音量は `voiceOptions` の下。`music` が加わる。トランシーバーの type に 2（持っていない）が加わる。
- ユーザーの許可: 判定の条件をまったく同じに保つなら、判定の処理を読みやすく書き直してよい（計画書の R8）。

## Fixed

### 1. 共有の型とスキーマ（`packages/shared`）
- `PlayerData` を新しい形式にする（`docs/VOICE_RULES.md` の「入力」の表と送信側のコードのとおり）。数値の項目はすべて有限の数値。
- `playerDataSchema` を新しい形式にする。古い平らな形式（`x` / `dimension` が最上位にあるもの）は受け付けない。理由: Minecraft 側と同時に更新するため。古い形式を受け取ったら、backend がログで分かるようにする（下の 2）。

### 2. 受信（`backend/src/gameReceiver.ts`）
- 実データのサンプルが届いたので（Q14）、型の検証を厳しくする: プレイヤーごとに `playerDataSchema` で検証する。
- **不正なプレイヤーはその人だけを取り除き**、ほかのプレイヤーは受け付ける。取り除いたことを、理由ごとに 1 分に 1 回までログに出す（古い形式なら「旧形式」と分かる文言にする。プレイヤー名はログに出さない）。理由: 1 人の不正なデータで全員の通話を止めないため。
- 配列でない・人数超過は今どおり 400。全員が不正でも 200 で、空の配列として扱う。
- 値は変換しない（受け取ったまま配信する）。

### 3. 聞こえる条件（`frontend/services/volume.ts`）
- `docs/VOICE_RULES.md` の「判定の順序」（手順 1〜11）と「受信と再生」をそのまま実装する。
- **書き直してよい（R8）**: 手順を上から順に評価する読みやすい形（例: 規則の配列や早期 return）にしてよい。ただし結果は 1 つも変えない。外側の変数の使い回し（`coef` など）はなくす。
- 判定結果に「どの手順で決まったか」（例: `admin` / `offGame` / `server` / `music` / `phone` / `transceiver` / `radio` / `dimension` / `distance`）を付け、診断情報（O1）の判定理由に使う。
- 受信の判定（`shouldSubscribe`）は今と同じ「結果が 0 より大きい、または全体発言」。

### 4. テスト（最重要）
- **既存の 41 ケースは、入力を新しい形式に置き換えるだけで、期待値を変えない。** 新しい項目は中立の値（同じ `server`、`music` 0、`radio.type` 2、トランシーバーは今の type と number をそのまま移す）にする。これで今の判定が保たれていることを確かめる。
- 新しい条件のケースを追加する（`docs/VOICE_RULES.md` の各行と「決定事項」A〜D に 1 つ以上ずつ）:
  - サーバー違い: 距離 0・同じ番号の通話・トランシーバー・ラジオでも 0。全体発言なら 1。
  - 音楽: L=2・S=1 なら、距離 0・通話・トランシーバー・ラジオでも 0、全体発言なら 1。L=2・S=0 / S=2、L=0・S=1、L=1・S=1 は聞こえる（ほかの条件どおり）。
  - ラジオ: S=1・L=0・同じ番号 → 1（距離 1000・別ディメンションでも）。S=1・L=1 → ラジオでは聞こえない。番号違い → ラジオでは聞こえない。S か L が type 2 → ラジオでは聞こえない。
  - ディメンション -1: L か S が -1 なら、距離 0 でも 0（-1 どうしも）。-1 でも通話・トランシーバー・ラジオ・全体発言なら聞こえる。
  - トランシーバーの type 2（持っていない）は、番号が一致しても聞こえない。
  - 判定理由が正しい手順を指すこと。
- 受信: 新しい形式を受け付ける／古い形式のプレイヤーは取り除かれる／一部の不正なプレイヤーだけが取り除かれる／全員不正で `[]`。

### 5. 偽ゲームサーバー（`backend/scripts/`）
- 送るデータを新しい形式にする。`set` コマンドは入れ子の項目をドット区切りで指定できるようにする（例: `set 1 location.server 2`、`set 0 music 2`、`set 1 radio.type 1`、`set all radio.number 5`）。今の平らな名前（`dimension` / `x` / `transceiverType` など）は使えなくなるので、ヘルプと `docs/MANUAL_TEST.md` を直す。
- `--replay` は新しい形式の記録（`docs/data/送信データ/*.jsonl` と同じ形）をそのまま送れること。
- シナリオ（static / sweep / walk）は新しい形式で動くこと。

### 6. frontend のそのほかの読み取り
- 自分のデータの `hasTelephone`（スマホのロール）と `mute`（ゲームからのミュート指示）の読み取りを新しい形式に合わせる（どちらも最上位のまま）。
- 距離の計算は `location.coordinates` を使う。

### 7. E2E
- 送るデータを新しい形式にし、新しい条件を確かめる項目を足す: サーバー違いで聞こえない／音楽（L=2・S=1）で聞こえないが全体発言は聞こえる／ラジオは発信から受信の一方向だけ／ディメンション -1 で距離の声が聞こえない。
